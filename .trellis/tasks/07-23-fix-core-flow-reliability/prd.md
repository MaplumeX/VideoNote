# 修复核心链路七项缺陷

## Goal

修复视频笔记核心链路中已确认的七项可靠性、数据一致性与权限缺陷，使用户从上传或提交 URL、观察处理进度、取消或恢复任务，到编辑保存和组织笔记的全过程不会无故卡住、丢失数据、产生无效费用或突破用户数据边界。

## Background

当前核心链路为：

`登录/刷新鉴权 → URL 提交或文件上传 → 后台视频处理 → SSE 进度 → 结果持久化 → 笔记编辑/自动保存 → 标签组织`

只读审查确认：

1. `frontend/src/pages/NoteDetailPage.tsx:171-193` 的自动保存使用可变 ref 和陈旧闭包，可能漏存首次编辑，或把尚未提交的新版内容错误标记为已保存。
2. `frontend/src/hooks/useVideoUpload.ts:24-26` 把语言放入 multipart body，而 `backend/app/api/routes.py:352-357` 把语言声明为 query 参数，本地上传实际总是回退为英文。
3. `frontend/src/hooks/useSSE.ts:39-49` 在每个网络 chunk 内重置事件解析状态，合法分包可能丢失 progress/complete 事件。
4. `backend/app/api/routes.py:317,394-396,606-608` 只用进程内 `asyncio.create_task()` 执行任务，`backend/app/main.py:17-20` 启动时没有非终态任务恢复逻辑。
5. `frontend/src/auth/api.ts:55-85` 的刷新等待队列在刷新失败时不会 reject，导致并发请求永久 pending。
6. `backend/app/api/routes.py:617-634` 的取消接口只更新 SQLite 状态，后台下载、转写和 LLM 生成仍继续运行。
7. `backend/app/api/note_routes.py:272-292` 接受任意 `tag_ids`，未验证标签属于当前用户；`backend/app/db.py:850-860` 也没有数据库侧用户边界。

历史任务表明项目曾主动移除 Redis/ARQ，采用 SQLite + 单进程部署以降低部署复杂度；重启恢复、多 Worker、任务取消当时明确不在范围内。本任务需要在不无意破坏现有单镜像部署体验的前提下补齐这些能力。

## Requirements

### R1 自动保存数据一致性

- 每次保存必须绑定不可变的 Markdown 快照；成功后只能把该快照标记为已保存。
- 首次或单字符编辑停止 1.5 秒后也必须触发保存。
- 保存期间产生的新编辑必须保留为 dirty，并在当前请求结束后继续保存，不能被旧响应覆盖或误标为已保存。
- 同一笔记的保存请求不得因响应乱序造成数据回退。
- Cmd/Ctrl+S 继续支持立即保存并取消待执行的防抖。
- 自动保存不得重建 Milkdown 编辑器，不得打断焦点、光标、IME 或 undo/redo。

### R2 上传语言契约

- 文件上传的 `language` 必须作为 multipart 表单字段由后端解析。
- 支持的语言保持 `en` 与 `zh-CN`，非法值继续通过现有归一化逻辑回退。
- URL 提交接口保持兼容。

### R3 SSE 协议解析与断线兜底

- SSE 解析状态必须跨网络 chunk 保留。
- 正确处理 CRLF/LF、任意字段分包、JSON 分包、多个 `data:` 行和流结束。
- 短暂断线时查询任务当前状态；任务已完成则获取结果，仍在处理则有限重连，不能直接把后台任务误判为失败。
- Hook 卸载或 job 切换后必须停止旧连接和重连。

### R4 重启后的任务终态保证

- 服务重启后，数据库里的非终态任务不能永久停留在处理中。
- URL 与本地上传任务都必须获得可观察的恢复或明确失败结果。
- 任务执行所需的输入必须持久化到 SQLite/持久卷，直到任务进入终态。
- 恢复执行必须避免重复并发领取同一任务，并保证终态写入幂等。
- 保持现有 API 路径和单镜像 Docker 部署方式兼容。

### R5 鉴权刷新并发安全

- 同一页面内并发 401 只能触发一次 refresh 请求。
- 所有等待请求在刷新成功后重试一次；刷新失败时全部 reject，不能永久 pending。
- API 请求最多自动重试一次，避免刷新循环。
- access token 继续仅保存在内存中，不写入 localStorage/sessionStorage。
- XHR 上传遇到过期凭据时必须给出明确、可恢复的行为。

### R6 任务取消

- 取消请求必须设置持久化取消意图，并阻止任务进入后续处理阶段。
- 当前进程内可取消的 asyncio 任务、子进程或异步网络请求应立即终止。
- 无法撤回的已发第三方请求返回后，不得继续下一阶段或写入完成结果。
- 取消必须清理临时文件，最终状态保持 `cancelled`。
- 删除运行中任务不得留下继续消耗资源且无法追踪的后台工作。

### R7 标签用户边界

- 给笔记添加已有标签时，笔记和所有标签必须属于同一当前用户。
- 混合合法与非法标签的请求必须整体失败，不能部分写入。
- 数据库写入函数必须包含用户作用域，不能只依赖路由层调用者记得校验。
- 迁移或启动检查必须清理潜在的历史跨用户标签关联。
- 对越权标签统一返回不泄露存在性的 404 结构化错误。

### R8 测试与兼容

- 为七项缺陷增加针对性回归测试，外部 yt-dlp、ASR、LLM 调用使用 mock。
- 保持现有 URL、上传、进度、结果、编辑、标签 API 路径兼容。
- 所有新增用户可见错误必须使用结构化错误码和中英文 i18n。
- 前端 lint、类型检查和生产构建通过；后端 pytest 与 Ruff 通过。

## Acceptance Criteria

- [x] AC1：只编辑一个字符并停止输入，1.5 秒后服务器保存该字符。
- [x] AC2：保存请求未返回时继续编辑，旧请求返回后 UI 仍显示 dirty，并最终把最新版本保存到服务器。
- [x] AC3：中文界面上传本地视频时，任务记录和笔记生成调用收到 `zh-CN`。
- [x] AC4：SSE 消息在每个字符边界进行分包时，progress 和 complete 仍只被正确派发一次。
- [x] AC5：SSE 短暂断线后，已完成任务进入笔记页；未完成任务恢复进度连接；取消或失败任务显示对应终态。
- [x] AC6：服务在 URL 或上传任务处理中重启后，任务会恢复执行或进入明确可重试失败态，不会无限处理中。
- [x] AC7：多个 API 同时收到 401 且 refresh 失败时，所有调用都结束为失败并进入统一登出流程。
- [x] AC8：多个 API 同时收到 401 且 refresh 成功时，只发起一次 refresh，每个原请求最多重试一次。
- [x] AC9：取消任务后不再启动任何后续阶段，不写入完成结果，并清理可清理的文件/进程。
- [x] AC10：用户不能把其他用户的标签关联到自己的笔记，混合标签请求无部分写入。
- [x] AC11：既有用户、任务、结果、合法标签关联和加密设置在迁移后保持可用。
- [x] AC12：后端 pytest/Ruff、前端 lint/typecheck/build 全部通过，工作区不存在非预期生成物。

## Out of Scope

- 任务优先级和定时任务。
- 横向多实例的高吞吐调度优化，除非所选恢复方案为正确性所必需。
- 笔记版本历史、多人协作编辑和离线编辑队列。
- 将 access token 改存浏览器持久存储。
- 更换 SQLite 数据库或重构全部 API。

## Key Decision

- 保持现有单镜像、SQLite、无 Redis/ARQ 的部署架构。
- 使用 SQLite 持久化可恢复输入和取消意图；单进程内保留后台任务强引用并在应用启动时重新调度非终态任务。
- 本任务保证当前单实例部署下的正确性，不承诺多实例分布式任务调度。
