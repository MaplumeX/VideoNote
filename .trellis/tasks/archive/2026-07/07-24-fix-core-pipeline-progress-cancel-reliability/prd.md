# 修复核心链路进度反馈与取消恢复可靠性

## Goal

修复 VideoNote 核心链路（提交 → 字幕/ASR → LLM 生成 → SSE 进度 → 完成/取消/重试/恢复）中存在的进度语义错乱、取消不深入阻塞调用、恢复无上限、长视频笔记截断与无进度、重复提交、错误信息泄漏等问题，使进度反馈准确、取消真正生效、长任务可观测、成本可控。

## Background

前序任务（07-23/07-24）已完成语言感知字幕、缩略图隔离、单例 DB、ASR 进度、SSE 心跳、yt-dlp 错误分类、LLM 重试、分段笔记生成等。本次聚焦残留的进度反馈语义、取消/恢复健壮性、长视频笔记与成本/安全类缺陷。

## Requirements

### R1 进度单调与语义正确
- R1.1 URL 流程：无字幕回落 ASR 时，进度不得从 0.2/0.5 回退到 0.2 再升。下载音频与转写使用独立、单调递增的进度区间。
- R1.2 上传文件流程：提取音频阶段不得标记为 `transcribing`；step 指示器对上传类任务不得显示「下载」步骤为 pending。

### R2 前端展示 progress.message
- R2.1 `NewNotePage` 处理中必须在 StepIndicator 区域展示后端推送的 `progress.message`（实时更新），长耗时段落用户可见「当前在做什么」。

### R3 失败步骤定位准确
- R3.1 `StepIndicator` 在 failed/cancelled 时不得把所有步骤标红；应仅标红失败发生所在阶段及其后续阶段，或仅标红当前阶段。

### R4 取消深入阻塞调用
- R4.1 取消请求应尽快终止底层 yt-dlp / ffmpeg / OpenAI 同步请求，避免用户取消后仍持续消耗 ASR/LLM token 与带宽。
- R4.2 在长耗时分段操作（LLM 多 chunk、ASR 多 chunk）的每一段之间插入取消检查点。

### R5 恢复上限
- R5.1 任务恢复调度须有最大尝试次数上限；超过上限的任务标记为 failed 并附可读原因，不再无限重试。

### R6 长视频笔记进度与截断处理
- R6.1 多 chunk 笔记生成与合并过程须分阶段上报进度（如「生成笔记 2/5」「合并笔记…」），不得全程停在 0.7。
- R6.2 LLM 输出被 `max_tokens` 截断时须可检测并续写，避免笔记不完整。

### R7 重复提交去重
- R7.1 同一用户对同一视频 URL 在已有进行中任务时，提交应被去重或拒绝，返回既有 job_id 或明确错误，避免重复消耗成本。

### R8 错误信息不泄漏
- R8.1 `/models` 端点异常时不得把内部 `str(e)`（含 endpoint/header/栈信息）直接透传给前端；返回通用可读错误码。
- R8.2 上传文件提取音频失败时错误码语义正确（不得用 `VIDEO_FETCH_FAILED`）。

## Acceptance Criteria

- [ ] URL 任务无字幕回落路径进度全程单调不减（手动追踪日志或断言验证）。
- [ ] 上传文件任务前端步骤指示器不再出现「下载 pending」错位。
- [ ] 处理中界面实时显示后端 `progress.message`。
- [ ] 失败时仅当前及后续步骤标红，而非全部。
- [ ] 取消一个正在 ASR/LLM 调用中的任务，底层同步请求被尽快中止（线程内可见取消信号或请求被中断）。
- [ ] 一个永久失败的任务在重启恢复超过上限后被标记 failed，不再被重新调度。
- [ ] 长视频（transcript > 60000 字符）笔记生成期间进度有细分更新；LLM 截断可被检测并续写完成。
- [ ] 同一 URL 重复提交被去重，不产生重复 job。
- [ ] `/models` 失败响应不含原始异常字符串；上传提取音频失败错误码语义正确。
- [ ] 既有核心链路回归测试通过；新增覆盖以上行为的测试通过。

## Scope / Non-Goals

- 不重写任务调度架构（仍为单进程 `TaskRunner`）。
- 不引入新的 job 队列或外部 broker。
- 不改动鉴权 / 加密 / 笔记组织（文件夹/标签/收藏）逻辑。
- 不改动 Milkdown 编辑器渲染管线。

## Notes

- 优先最小改动；不重构无关代码。
